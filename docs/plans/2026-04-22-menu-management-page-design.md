# 菜单管理页补全设计方案

## 1. 背景

当前仓库中的菜单管理页仍为静态占位页，前端只展示示例树和预留按钮，但后端已经具备菜单树、菜单详情、创建、更新、删除等完整接口。

结合当前项目阶段，菜单管理页应按照后台统一页面模板补齐为可用页，并保持与部门管理页一致的“树加详情”交互方式。

## 2. 目标

- 将菜单管理页从占位页补全为真实业务页
- 完成菜单树查询、菜单详情、创建、更新、删除
- 采用“树 + 详情 + 抽屉表单”的页面结构
- 与现有后端菜单接口直接对齐
- 同步更新主设计文档中的菜单页说明

## 3. 非目标

- 本次不重做角色页
- 本次不增加菜单启停接口
- 本次不做按钮级资源管理
- 本次不做菜单多语言、多租户隔离、版本发布

## 4. 设计原则

- 使用树加详情页模板，参考阿里系中后台常见模式
- 保持在页面中：新增、编辑优先用抽屉完成
- 后端真校验，前端负责体验和输入约束
- 与现有用户页、部门页交互风格保持一致

## 5. 页面结构

- 左侧：菜单树
  - 展示完整菜单层级
  - 点击节点加载右侧详情
- 右侧：菜单详情卡片
  - 展示编码、名称、类型、父节点、路由、组件、图标、排序、最小权限等级、备注
  - 顶部操作：新增根菜单 / 新增子菜单 / 编辑 / 删除
- 抽屉：菜单表单
  - 创建与编辑复用同一个抽屉组件

## 6. 交互设计

- 新增根菜单
  - 打开抽屉，默认 `parentId = 0`
- 新增子菜单
  - 仅在当前节点为 `CATALOG` 时展示
  - 打开抽屉并带入当前菜单作为父节点
- 编辑菜单
  - 复用表单抽屉
  - `menuCode` 只读
- 删除菜单
  - 使用危险操作确认
  - 后端继续负责“有子菜单不可删除”等规则校验

## 7. 前后端契约

菜单管理页直接对接以下接口：

- `GET /api/v1/menus/tree`
- `GET /api/v1/menus/{id}`
- `POST /api/v1/menus`
- `PUT /api/v1/menus/{id}`
- `DELETE /api/v1/menus/{id}`

## 8. 前端实现范围

- 扩展 `frontend/src/api/modules/menu.ts`
- 扩展 `frontend/src/types/menu.ts`
- 新增 `frontend/src/views/menu/components/MenuFormDrawer.vue`
- 改造 `frontend/src/views/menu/MenuTreeView.vue`

## 9. 测试与验证

- 后端菜单接口已有控制层测试覆盖，不额外新增后端测试
- 前端通过 `vue-tsc --noEmit` 做类型检查

## 10. 文档同步

实施完成后更新：

- `docs/project-design.md`
  - 菜单管理页页面结构

## 11. 结论

本方案以最小增量方式补齐菜单管理页，使其与部门管理页保持统一的树加详情操作模式，并直接复用现有后端菜单接口形成完整闭环。
