# 后台前端搭建设计方案

## 1. 背景

当前仓库已经具备较完整的后端管理能力，包括认证、用户、部门、角色、菜单、权限、同步任务以及第三方 LDAP 接入控制面，但仓库内尚未存在前端工程。

结合当前阶段目标，前端首期不追求完整产品化设计系统，也不优先做可视化大屏，而是优先搭建一套可以稳定承接现有后端接口的后台管理台。

本方案采用：

- `Vue 3 + Element Plus` 作为默认实现栈
- 参考阿里系中后台设计方法论组织信息架构、导航、表单、列表和反馈
- 以“最快形成业务闭环”为第一优先级

## 2. 目标

- 在最短路径内搭出可扩展的后台前端骨架
- 与当前后端接口契约直接对齐，减少中间适配层
- 统一登录、路由、菜单、状态管理和接口访问方式
- 使用稳定的页面模板，避免每个业务页各写一套
- 在首期就为后续扩展到第三方 LDAP、飞书导入、批次详情预留清晰结构

## 3. 非目标

- 首期不做重型设计系统平台
- 首期不做多主题、暗黑模式、国际化
- 首期不做复杂前端按钮级 ACL 引擎
- 首期不引入 Tailwind、微前端、低代码平台等高复杂度方案
- 首期不追求视觉“炫技”，以企业后台的稳定性和可读性优先

## 4. 设计原则

本方案参考阿里系中后台常见方法，采用以下设计原则：

- 信息分层优先：先区分导航层、页面层、操作层、数据层，避免一个页面同时承担过多任务
- 任务导向优先：用户进入后台是为了完成“查、改、配、触发任务、看结果”，页面应围绕任务流程组织
- 保持在页面中：新增、编辑、状态变更、批量操作优先使用抽屉和对话框，减少无意义跳转
- 一致性优先：查询区、表格区、详情区、危险操作、成功/失败反馈采用统一模板
- 后端真鉴权，前端做体验：前端控制菜单可见性和页面导航，真正权限判定以后端 403 为准
- 先骨架后细节：先打通登录、布局、菜单、核心 CRUD，再扩展 LDAP 与同步控制面

## 5. 推荐技术栈

### 5.1 核心栈

- `Vue 3`
- `TypeScript`
- `Vite`
- `Vue Router`
- `Pinia`
- `Element Plus`
- `Sass`

### 5.2 推荐补充栈

- `Axios`
  - 原因：简单直接，和当前项目首期复杂度匹配
- `@tanstack/vue-query`
  - 原因：统一服务端状态缓存、重试、失效与加载态
- `VueUse`
  - 原因：减少常见组合式逻辑的重复实现
- `pinia-plugin-persistedstate`
  - 原因：持久化 token、侧边栏折叠状态、用户偏好
- `unplugin-auto-import`
  - 原因：减少组合式 API 和工具函数样板代码
- `unplugin-vue-components`
  - 原因：自动按需引入 Element Plus 组件
- `@element-plus/icons-vue`
  - 原因：统一后台图标来源
- `echarts`
  - 原因：后续首页统计卡片和简单趋势图足够使用
- `eslint + prettier + stylelint + husky + lint-staged`
  - 原因：首期就把工程质量底线立住
- `openapi-typescript`
  - 原因：后端已经提供 springdoc，前端可基于 OpenAPI 生成类型，减少手写接口类型漂移

### 5.3 不推荐首期引入的栈

- `Tailwind CSS`
  - 原因：会引入第二套样式语言，和 Element Plus 并用成本较高
- `Ant Design Vue`
  - 原因：虽然更贴近阿里系视觉，但偏离你指定的默认技术栈
- `Nuxt`
  - 原因：当前是纯后台管理台，不需要 SSR
- `微前端`
  - 原因：当前项目体量和团队阶段不需要

## 6. 总体方案

### 6.1 推荐方案

采用“`Element Plus 组件层 + 项目级页面模板层 + 业务模块层`”三层结构。

含义如下：

- 组件层只负责基础 UI 能力，不直接承载业务规则
- 页面模板层负责沉淀后台通用布局和交互模式
- 业务模块层负责用户、部门、角色、菜单、同步、LDAP 等领域页面

这样做的好处是：

- 首期可以快速搭建
- 后续不会因为直接堆页面导致结构失控
- 保持和 Element Plus 兼容，不需要自建整套组件库

### 6.2 页面组织方法

后台页面优先沉淀为以下几类模板：

- 查询列表页
  - 适用：用户、角色、同步任务
- 树加详情页
  - 适用：部门、菜单
- 配置关系页
  - 适用：角色菜单绑定、角色权限授权、用户角色分配
- 任务结果页
  - 适用：同步批次详情、对账详情
- 表单加结果页
  - 适用：LDAP 预检、第三方模板查看

## 8. 布局方法

### 8.1 全局布局

采用经典中后台布局：

- 顶部 Header
  - Logo
  - 面包屑
  - 当前用户
  - 退出登录
- 左侧 Sider
  - 一级导航
  - 支持折叠
- 中间 Main
  - PageHeader
  - 查询区
  - 内容区

### 8.2 布局规范

- 使用 8px 网格思路控制间距
- 页面级常用间距统一使用 `16 / 24 / 32`
- 内容区统一采用卡片容器，不让表格直接裸贴页面背景
- 表格页优先“查询区在上、表格在下、批量操作贴近表格”
- 树页面采用“左树右详情”或“左列表右内容”的稳定结构

### 8.3 视觉方向

首期推荐采用：

- 浅色主内容区
- 深色或偏中性色侧边导航
- 主色使用企业蓝，不追求高饱和品牌化
- 强调状态标签、表格可读性、表单清晰度

这更适合：

- 后台长时间使用
- 数据密集型页面
- 与 Element Plus 默认能力快速结合

## 9. 交互方法

### 9.1 登录与认证

前端首期认证流程：

- 登录页调用 `/api/v1/auth/login`
- 登录成功后保存 token
- 应用启动时调用 `/api/v1/auth/me`
- 路由进入后台前做登录态校验

### 9.2 菜单与路由

推荐做法：

- 路由按模块静态注册
- 菜单数据优先对接后端 `self tree` 接口
- 如果首期后端菜单返回不足以直接驱动路由，则先以前端静态菜单兜底

首期建议：

- 不做复杂动态路由生成器
- 先采用“静态路由 + 菜单可见性控制”的低风险方案

### 9.3 权限策略

首期权限控制方法：

- 菜单是否展示，由登录后拿到的当前用户信息和菜单树决定
- 页面是否可进入，由路由守卫控制
- 按钮是否显示，采用页面内粗粒度配置
- 真正的权限校验以后端返回结果为准

这样做的原因：

- 当前后端已经具备 Casbin 鉴权
- 前端若首期再自建一套按钮权限表达式体系，投入高、收益低

### 9.4 表单与反馈

统一采用：

- 小表单变更用对话框
- 中等复杂度编辑用抽屉
- 高复杂度配置用独立页面
- 危险操作必须二次确认
- 异步任务必须有加载、成功、失败三态反馈

## 11. 工程设计

### 11.1 目录结构

推荐目录：

```text
frontend/
  src/
    api/
    assets/
    components/
    composables/
    constants/
    layout/
    router/
    stores/
    styles/
    types/
    utils/
    views/
      auth/
      dashboard/
      user/
      department/
      role/
      menu/
      permission/
      sync/
      profile/
```

### 11.2 分层约束

- `api/` 只放接口调用和 DTO 类型
- `stores/` 只放全局状态，不堆业务细节
- `views/` 只做页面编排
- `components/` 只放通用业务组件和页面模板组件
- `composables/` 放可复用逻辑，如分页、查询条件、表单提交、请求状态

### 11.3 样式策略

统一采用：

- 全局 token 放在 `styles/variables.scss`
- 页面局部样式使用 `scoped + BEM`
- 不直接覆盖 Element Plus 大量内部类名
- 对 Element Plus 主题只做必要 token 定制

### 11.4 接口策略

推荐采用：

- `api/modules/*.ts` 按业务域拆分接口
- 请求响应统一经过 `request.ts`
- 统一处理 token、超时、401、403、500
- 统一把后端 `ApiResponse` 解包

### 11.5 状态管理策略

Pinia 首期只保留以下核心 Store：

- `authStore`
- `appStore`
- `menuStore`

原则：

- 列表页数据尽量交给 `vue-query`
- 不要把所有页面数据都塞进 Pinia

## 12. 代码规范

前端编码规范遵循以下原则：

- 全量使用 TypeScript
- 开启严格模式，避免首期遗留大量 `any`
- 组合式 API 优先，不再使用 Options API
- 业务类型和接口类型分离
- 页面逻辑超过一定复杂度时提取为 composable
- 表格列定义、表单 schema、状态枚举集中管理
- 文案、状态色、危险操作文案保持统一

## 15. 风险与控制

### 15.1 菜单驱动不完整风险

如果后端菜单树暂时不能完整承载前端路由：

- 首期先静态路由
- 菜单树只控制可见性
- 后续再升级为真正的动态菜单驱动

### 15.2 前端权限过度设计风险

如果首期就强做复杂按钮权限系统：

- 会拖慢首期进度
- 容易和后端 Casbin 规则重复

控制方式：

- 前端做体验控制
- 后端做最终判定

### 15.3 页面风格漂移风险

如果没有统一模板：

- 列表页会出现多种查询区写法
- 表单页交互会不一致

控制方式：

- 先沉淀页面模板组件
- 业务页只基于模板组装

## 16. 结论

本方案的核心不是“做一个花哨的 Vue 后台”，而是以 `Vue3 + Element Plus` 为基础，按阿里系中后台方法把现有后端能力快速组织成一套可持续扩展的管理台。

首期推荐坚持以下取舍：

- 先跑通后台骨架和核心业务页
- 先采用稳定布局和统一页面模板
- 先让后端权限做最终控制
- 先少引入技术栈，避免工程复杂度膨胀

这样最适合当前项目阶段，也最利于后续直接进入真正的前端实现。
