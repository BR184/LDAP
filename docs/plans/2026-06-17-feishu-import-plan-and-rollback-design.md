# 飞书花名册计划式导入与撤回设计方案

**状态：** Proposed

**日期：** 2026-06-17

**修订日期：** 2026-06-18

**目标：** 将飞书花名册导入能力改造成单入口、计划式、可确认、可撤回的同步体系。平台不再让用户选择 `MERGE` / `ALIGN` 等模式，而是在一次导入预览中展示所有将要发生的变更，由用户按条确认、关闭后执行。执行后支持撤回和 LDAP 一致性补偿。

---

## 1. 核心身份模型

### 1.1 最终规定

当前代码采用的身份模型是正确方向，本方案确认沿用：

```text
飞书 user_id = 平台 sys_user.user_id = LDAP uid
```

三者含义如下：

| 概念 | 存储位置 | 说明 |
| --- | --- | --- |
| 飞书外部 ID | 飞书导入文件中的 `user_id` | 公司统一人员 ID 的来源 |
| 平台登录 ID | `sys_user.user_id` | 平台账号 ID |
| LDAP uid | LDAP 用户条目的 `uid` | GitLab、邮箱等外部系统登录 ID |

也就是说，飞书 `user_id` 是统一身份源头，平台账号和 LDAP 账号都以它为准。

### 1.2 为什么不做外部身份绑定表

本项目当前只确认飞书作为公司人员身份主来源。若额外引入 `sys_user_external_identity`，会带来不必要的模型复杂度：

- 会把“一个人一个统一账号”的模型拆成平台账号和外部身份两套概念。
- 会增加导入匹配、撤回、LDAP 同步、权限判断的复杂度。
- 会与当前 V24/V25 迁移后的代码方向冲突。
- 会让后续开发为了兼容两套身份模型而堆出维护成本。

因此本方案不新增外部身份绑定表，不回退当前代码身份模型。

### 1.3 手工录入规则

两次飞书导入之间，管理员可能先手工录入实习生或临时员工。

手工录入不是另一套身份来源，也不是临时账号。管理员手工输入的 `user_id` 仍然必须是飞书 `user_id`。

- 飞书文件导入：系统从飞书导出文件读取 `user_id`。
- 手工录入：管理员从飞书或交接信息中手工填写 `user_id`。
- 两种方式写入的都是同一个平台用户。
- 后续飞书文件导入遇到相同 `user_id` 时，只生成字段补全或字段更新项。
- 手工录入用户已有角色、权限、本地邮箱和特殊配置不得被后续导入覆盖。

如果管理员无法取得飞书 `user_id`，不应创建正式平台账号。此类情况应先补齐飞书身份 ID，再录入平台。

## 2. 单入口计划式导入

前端只提供一个用户能理解的动作：

> 导入飞书花名册

不再向用户暴露 `MERGE`、`ALIGN`、`SUPPLEMENT` 等模式选择。

导入固定分为两步：

1. `PLAN`：解析文件，计算差异，生成持久化导入计划，不修改业务数据。
2. `EXECUTE`：按用户确认后的计划执行，只修改仍处于启用状态的变更项。

导入计划必须持久化，不能只存在前端内存中。

## 4. 导入计划内容

导入计划需要展示以下类别：

- 新增用户
- 用户字段更新（含手工录入后飞书补全）
- 离职或禁用用户
- 新增部门
- 部门字段更新
- 部门禁用
- LDAP 修复项
- 冲突项
- 无变化项

每条变更展示：

- 目标对象
- 字段名
- 原值
- 新值
- 变更原因
- 默认动作
- 是否执行开关
- 是否需要确认
- 风险级别

管理员可以关闭某条变更。关闭后该变更本次不执行，但仍保留在导入计划中作为审计记录。

## 5. 用户匹配规则

导入计划生成时按以下顺序匹配用户：

1. 使用导入文件中的飞书 `user_id` 作为 `sys_user.user_id` 进行查询。
2. 如果找到匹配的用户，目标用户就是该平台用户（更新模式）。
3. 如果未找到匹配用户，则生成新增用户项（新用户的 `user_id` 直接使用飞书 `user_id`）。
4. 如果同一 `employee_no` 已属于其他未删除用户，生成阻断冲突。
5. 如果匹配到多个用户，生成阻断冲突。

禁止使用姓名加手机号自动合并用户。

姓名加手机号只能用于提示”疑似同一人”，由管理员人工处理。自动合并只能基于飞书 `user_id`。

---

## 6. 阻断级冲突

存在阻断级冲突时，确认导入按钮置灰。

阻断冲突包括：

- 同一个飞书 `user_id` 在导入文件中重复。
- 同一个工号在导入文件中重复。
- 同一个工号在平台中对应多个未删除用户。
- 飞书 `user_id` 匹配到用户 A，但工号匹配到用户 B（疑似离职后新员工复用工号）。
- 飞书用户工号变更后撞上其他平台用户。
- 部门树存在循环。
- 用户引用的主部门无法匹配。
- LDAP uid 将与已有非本用户条目冲突。
- LDAP group DN 重命名后与已有 group 冲突。
- 导入计划已过期。
- 目标对象版本与计划生成时不一致。

---

## 7. MySQL 与 LDAP 一致性补偿

MySQL 支持事务，LDAP 不支持与 MySQL 处于同一个本地事务中。因此导入执行不能假设“两边同时成功”。每条变更项必须具备可观测、可重试、可补偿的状态机。

变更项状态：

- `PENDING`：待执行。
- `MYSQL_PENDING`：准备写 MySQL。
- `MYSQL_DONE`：MySQL 已完成。
- `LDAP_PENDING`：等待写 LDAP。
- `LDAP_DONE`：LDAP 已完成。
- `COMPLETED`：业务变更完整完成。
- `SKIPPED`：用户关闭，本次跳过。
- `MYSQL_FAILED`：MySQL 写入失败。
- `LDAP_FAILED`：LDAP 写入失败。
- `COMPENSATION_PENDING`：等待补偿。
- `COMPENSATION_FAILED`：补偿失败，需要人工处理。

执行原则：

- MySQL 变更和 LDAP 变更都必须按变更项记录状态。
- LDAP 操作必须幂等。
- LDAP 写入失败时，不允许把批次简单标记为成功。
- 每次导入完成后必须触发本批次影响范围内的 MySQL/LDAP 对账。
- 对账发现不一致时，生成补偿项并支持重试。
- 自动重试默认最多 3 次，超过后进入人工处理。

建议新增或重构 LDAP 幂等接口（参数中的 `uid` 即为 LDAP uid，等同于 `sys_user.user_id`）：

注：当前代码中部分接口参数名仍为 `userId`，语义等同于 LDAP uid，未来可重构为更明确的 `uid` 命名。

- `createOrUpdateUser(User user, String initialPassword)`
- `disableUserIfExists(String uid)`
- `enableUserIfExists(String uid)`
- `syncUserGroupsToExactState(String uid, List<String> groupCodes)`
- `createOrUpdateGroup(Department department)`
- `removeUserFromAllGroupsIfExists(String uid)`

## 8. 撤回设计

### 8.1 撤回原则

撤回不是重新导入旧文件，也不是从审计日志猜测差异，而是基于执行前快照进行补偿。

撤回前必须生成撤回计划，展示将恢复哪些字段、禁用哪些新增对象、恢复哪些 LDAP 状态。用户确认后才执行撤回。

### 8.2 撤回策略

| 原变更类型 | 撤回动作 |
| --- | --- |
| 新增用户 | 统一禁用本次新增用户，并禁用 LDAP 用户、移除组关系；不默认物理删除 |
| 更新用户字段（含手工录入后飞书补全） | 恢复执行前字段值，并同步 LDAP |
| 离职或禁用 | 恢复执行前状态，并重新启用 LDAP |
| 新增部门 | 统一禁用本次新增部门；不默认物理删除 |
| 更新部门 | 恢复执行前字段，并同步 LDAP group |
| 角色默认绑定 | 只撤回本批次新增的默认角色，不影响用户后续人工授权 |

撤回不默认物理删除用户和部门。

如果未来确实需要物理删除，应作为独立的“清理回收”能力，由管理员明确选择，并单独审计。

### 8.3 撤回限制

撤回前必须检查：

- 原批次已成功执行。
- 原批次未被撤回。
- 原批次不存在 `LDAP_FAILED` 或 `COMPENSATION_FAILED` 未处理项。
- 当前没有其他飞书导入或撤回批次处于进行中。
- 后续批次没有修改同一个目标对象，或用户已确认冲突处理方式。
- 目标对象仍能被唯一定位。
- LDAP 当前状态没有不可恢复冲突。

## 9. 并发控制

飞书导入和撤回必须串行化。

批次级互斥：

- 同一时刻只允许一个飞书导入批次处于 `PLANNED`、`EXECUTING`、`ROLLBACK_PLANNED`、`ROLLING_BACK` 状态。
- 创建新导入计划前必须获取导入锁。
- 执行和撤回时必须持有同一类导入锁。
- 锁必须由数据库保证原子性。

对象级乐观锁：

- `sys_user`、`sys_department` 建议新增 `version` 字段。
- 导入计划生成时记录目标对象版本。
- 执行前校验当前版本与计划版本一致。
- 不一致则该变更项转为冲突，不再继续执行。

计划有效期：

- 导入计划增加 `valid_until`。
- 默认有效期为创建后 24 小时。
- 超期后不能执行，必须重新生成计划。

## 11. 后端服务分层

推荐服务：

- `FeishuImportPlanApplicationService`
  - 负责文件解析、身份匹配、字段差异计算、计划持久化。

- `FeishuImportExecutionApplicationService`
  - 负责执行已确认计划、写入 MySQL、同步 LDAP、生成撤回快照。

- `ImportRollbackApplicationService`
  - 负责生成撤回计划、执行撤回、恢复 MySQL 和 LDAP。

- `ImportConsistencyApplicationService`
  - 负责导入后 MySQL/LDAP 对账、补偿任务生成、失败项重试。

- `ImportDiffPolicyService`
  - 负责字段归属、字段锁定、风险等级、是否需要确认。

- `ImportConflictDetector`
  - 负责重复工号、重复 user_id、部门树异常、LDAP uid 冲突等检测。

- `ImportLockService`
  - 负责飞书导入、执行、撤回的批次级互斥锁。

- `ImportObjectVersionService`
  - 负责用户、部门等对象版本校验。

禁止采用以下实现：

- 在现有 `FeishuUserImportService` 中继续堆大量条件分支。
- 用前端临时状态保存用户关闭了哪些变更。
- 执行导入时重新按文件算一遍，而不是按持久化计划执行。
- 用审计日志反推撤回。
- 用姓名和手机号自动合并账号。
- 让飞书导入覆盖角色、权限、密码、本地邮箱。
- 把撤回实现成数据库字段简单改回，而不同步 LDAP。

## 12. 接口建议

- `POST /api/v1/system/imports/feishu/plans`
  - 创建导入计划。

- `GET /api/v1/system/imports/feishu/plans/{batchId}`
  - 查询导入计划。

- `GET /api/v1/system/imports/feishu/plans/{batchId}/items`
  - 查询变更项。

- `PATCH /api/v1/system/imports/feishu/plans/{batchId}/items/{itemId}`
  - 开启、关闭、确认某条变更。

- `POST /api/v1/system/imports/feishu/plans/{batchId}/execute`
  - 执行导入计划。

- `POST /api/v1/system/imports/feishu/plans/{batchId}/retry-failed`
  - 重试失败项。

- `POST /api/v1/system/imports/feishu/plans/{batchId}/rollback-plan`
  - 创建撤回计划。

- `POST /api/v1/system/imports/feishu/plans/{batchId}/rollback`
  - 执行撤回。

## 13. 实施阶段

### Phase 1：模型和规则落地

- 新增导入批次表。
- 新增导入变更项表。
- 新增撤回项表。
- 新增导入锁表或等价数据库原子锁机制。
- 为 `sys_user`、`sys_department` 增加 `version` 字段。
- 固化字段归属规则。
- 固化身份匹配规则。

### Phase 2：计划生成能力

- 重构飞书文件解析为纯输入解析能力。
- 新增计划生成服务。
- 生成用户、部门、LDAP 相关变更项。
- 生成计划有效期和对象版本快照。
- 检测飞书 user_id 变更、工号变更撞车、LDAP uid/group 冲突。
- 提供查询计划和查询变更项接口。

### Phase 3：计划调整和确认能力

- 支持单条变更开启、关闭、确认。
- 支持批量开启、关闭同类变更。
- 支持关闭原因。
- 前端完成计划展示与置灰规则。

### Phase 4：执行导入

- 按持久化计划执行，不重新从文件推导动作。
- 获取导入互斥锁。
- 执行前做计划过期、版本和冲突复检。
- 按变更项状态机写 MySQL。
- 按幂等 LDAP 接口同步 LDAP。
- 生成撤回快照。
- 执行后触发本批次影响范围内的 MySQL/LDAP 对账。
- 失败项进入可重试状态。
- 记录审计日志。

### Phase 5：撤回能力

- 生成撤回计划。
- 展示撤回影响。
- 获取撤回互斥锁。
- 执行撤回。
- 按默认禁用策略处理本批次新增用户和部门。
- 恢复 MySQL、LDAP 和本批次默认角色绑定。
- 记录撤回审计。

### Phase 6：一致性补偿能力

- 新增导入后对账服务。
- 新增失败项重试接口。
- 支持 LDAP 失败项最多自动重试 3 次。
- 超过重试次数后进入人工处理。
- 在导入历史中展示不一致项和补偿状态。

### Phase 7：替换旧入口

- 前端删除对 `SUPPLEMENT` / `ALIGN` 的用户可见模式选择。
- 后端旧接口统一收敛到新计划式导入服务。
- 旧接口如需临时保留，只能作为内部兼容入口，并标记废弃。

## 14. 验收标准

### 14.1 基础导入

- 上传飞书花名册后可以生成导入计划。
- 新增用户被展示为新增项。
- 已存在用户字段变化被展示为字段级更新项。
- 离职用户被展示为离职或禁用项。
- 用户可关闭任意非阻断变更。
- 执行时只执行启用项。
- 计划超过有效期后不可执行。
- 执行前目标对象版本变化时，对应项进入冲突状态。

### 14.2 手工录入用户补全

- 手工录入用户必须使用飞书 `user_id`。
- 下次飞书文件导入出现相同 `user_id` 时，应识别为同一平台用户，生成字段级更新项。
- 平台 `user_id` 和 LDAP uid 不发生变化。
- 手工录入用户已有角色和特殊权限不被覆盖。
- 撤回字段更新后，恢复执行前字段值，`user_id` 和 LDAP uid 保持不变。

### 14.3 权限和本地字段保护

- 导入不覆盖 `intranet_email`。
- 导入不覆盖用户角色。
- 导入不覆盖权限绑定。
- 导入不修改密码。
- 新用户自动绑定默认普通用户角色。
- 老用户已有角色时不强制改为普通用户。

### 14.4 冲突处理

- 文件中重复 user_id 生成阻断冲突。
- 文件中重复工号生成阻断冲突。
- 飞书 user_id 匹配用户 A、工号匹配用户 B 时生成阻断冲突。
- 工号变更撞上其他用户时生成阻断冲突。
- 主部门不存在生成阻断冲突。
- 部门树循环生成阻断冲突。
- LDAP uid 或 group DN 冲突生成阻断冲突。
- 计划过期或对象版本变化生成阻断冲突。
- 存在未决阻断冲突时不得直接执行；管理员必须先为每条冲突选择服务端声明的处理方式。

### 14.5 阻断冲突处理闭环

阻断冲突不得通过物理删除记录或单纯修改前端状态绕过。草稿计划提供三种安全出口：

- 按工号合并更新：仅当飞书 `user_id` 未匹配、但 `employee_no` 唯一命中一个现有账号时可用。系统将导入候选转换为现有账号的字段更新，保留数据库用户 ID、平台 `user_id`、LDAP uid/DN、内网邮箱、密码和角色绑定，并记录处理人、处理时间和处理动作。
- 排除冲突对象：将冲突标记为已排除，同时禁用并跳过与该冲突相关的新增、修改或离职变更；保留处理人、处理时间和处理动作。
- 取消草稿计划：将批次标记为 `CANCELLED`，保留完整计划和冲突记录，允许管理员修正源文件后立即重新生成计划。

只有状态仍为 `PENDING` 的 `BLOCKER` 才阻止计划确认。已处理的阻断项保留 `BLOCKER` 风险等级用于审计，但状态必须转为 `SKIPPED`；按工号合并产生的更新项进入正常确认和执行流程。

每个冲突必须持久化稳定的 `conflict_code`，接口根据冲突类型返回允许的处理方式。文件内重复、两个现有账号交叉命中、LDAP uid 占用等无法唯一判断身份的冲突不得提供强制合并入口。

历史草稿批次可能只有冲突编码而缺少候选快照。此时服务端只能依据批次保存的完整 SHA-256，在受控导入目录中重新定位原文件；源文件中的 `user_id` 和 `employee_no` 都必须唯一命中，且不得出现账号交叉匹配。恢复成功后，现有账号快照和导入目标快照必须在处理冲突的同一事务中写回冲突记录。源文件缺失、哈希不匹配或身份存在歧义时拒绝合并，不允许按文件名或姓名猜测。

XLSX 中的手机号可能被保存为数值单元格。解析器必须先按无科学计数法的数值文本读取，再执行国家码标准化，禁止把 `8.62E+12` 直接删除非数字字符后得到错误手机号。导入源文件目录扫描数量由外部配置限制，避免历史文件持续增长后形成无边界扫描。

生成计划时，如果某个用户或部门已经命中对象级冲突，不得继续为同一对象生成可执行变更。文件内重复 user_id、工号、部门 external_id 或部门编码时，所有受影响对象均不得生成可执行变更。

冲突与关联变更的匹配必须基于稳定标识：用户使用 `user_id` 或 `employee_no`，部门使用 `dept_code` 或 `external_id`。禁止依赖姓名、部门名称或界面显示文本。

### 14.6 撤回

- 成功执行的导入批次可生成撤回计划。
- 撤回计划展示将恢复或禁用的对象。
- 撤回新增用户后，该用户默认被禁用，LDAP 登录能力被禁用，组关系被清理。
- 撤回字段更新后，用户字段和 LDAP 条目恢复到执行前状态，`user_id` 和 LDAP uid 保持不变。
- 撤回离职后，用户状态和 LDAP 可登录状态恢复。
- 后续批次已修改同一对象时，撤回进入冲突状态，不直接执行。
- 撤回新增部门后，部门默认被禁用，不物理删除。
- 撤回前存在 LDAP 失败或补偿失败项时，不允许直接标记撤回完成。

### 14.7 MySQL 与 LDAP 一致性

- 导入执行中 MySQL 成功但 LDAP 失败时，变更项进入 `LDAP_FAILED`。
- 失败项可通过重试接口再次执行。
- LDAP 操作重复执行不会产生重复用户、重复组或重复成员。
- 批次执行后自动生成影响范围内的对账结果。
- 存在不一致项时，批次状态必须体现部分失败或待补偿。
- 补偿成功后状态变为 `COMPLETED`。

### 14.7 并发控制

- 已存在 `PLANNED` 或 `EXECUTING` 的飞书导入批次时，不能创建第二个导入计划。
- 撤回执行中不能创建或执行新导入。
- 同一批次不能被两个管理员同时撤回。
- 用户或部门在计划生成后被人工修改，执行时必须阻断相关变更项。

---

## 15. 最终结论

本方案确定采用：

```text
飞书 user_id = 平台 sys_user.user_id = LDAP uid
```

作为统一身份模型。

系统每次导入都生成完整、可审查、可调整、可执行、可撤回的导入计划。复杂性由后端规则、持久化计划、LDAP 补偿状态机和撤回快照承载，前端只表达一个清晰流程：检查这次导入会改变什么，关闭不想执行的变更，确认后执行。

这套设计避免继续在现有导入服务中叠加临时兼容分支，也避免引入不必要的外部身份绑定模型，为后续字段保护、本地特殊权限、LDAP 一致性补偿和灾难恢复留下清晰扩展点。
