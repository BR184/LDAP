# 角色组委派管理与开放角色供给 —— 需求与设计规格

> 本文档只定义"做什么、做成什么样、边界在哪"，不包含实现细节（代码、表结构、接口路径等）。实现方应依据本文档自行完成技术设计。

## 一、项目定位与背景

- 接入本平台的第三方系统普遍采用"用户—角色—权限"三层分离的 RBAC 架构。
- 本平台的定位是**统一身份与角色成员关系权威源**，只承担其中两层：
  - **用户层**：用户主数据的权威维护（飞书/LDAP 同步）。
  - **角色层**：角色定义，以及"哪些用户属于哪些角色"的成员关系。
- **权限层不归属本平台**。第三方系统拿到本平台的用户与角色成员关系后，在**自己平台内部**完成"角色→本地权限"的映射与授权。
- 因此本平台对外只交付**成员关系**（哪些用户属于哪些角色），不下发任何权限。

**要解决的问题**：约 300 名用户需要跨多个业务域/第三方系统维护成员关系。若全部由平台管理员逐人手工维护，不可持续。需要把"角色定义 + 成员关系维护"按业务域**委派给各业务域管理员自服务**，同时保证：委派者只能管自己的范围、开放给第三方的是带作用域隔离的只读查询、平台管理员保留全局监督与处置能力。

## 二、核心概念定义

以下概念在本文档中含义唯一，实现方不得引入额外含义。

| 概念 | 定义 |
|---|---|
| **角色组（Role Group）** | 一个由委派者创建并维护的角色容器。是"哪些角色归我管、我的令牌能看到哪些角色"的边界。组有名称、所有者、若干协作成员。 |
| **角色作用域** | 每个角色具有且仅具有下列三种作用域之一：**全局**（所有组可见、管理员维护）、**组**（归属某角色组、仅该组可见）、**系统级**（仅平台管理员可见，存量内置管理角色默认此类）。 |
| **全局角色** | 作用域为"全局"的角色，如"普通用户"。对所有组可见，任意组令牌都能取到。 |
| **组角色** | 作用域为"组"的角色，归某一个角色组所有。组角色是**成员集合**：只表达"哪些用户属于该角色"，**不携带本平台任何权限**。 |
| **委派权限** | 通过平台既有角色体系授予的一组能力，由两个不可分割的权限组成：**委派角色组管理** 与 **委派用户分配**。二者必须同时授予、同时撤销。 |
| **委派者** | 持有"委派角色组管理"权限的用户。 |
| **组管理员** | 同时满足"是某角色组成员"与"持有委派权限"的用户。组成员身份决定他属于哪些组，委派权限决定他能否真的执行管理。 |
| **所有者（OWNER）** | 组的最高权限成员：组设置、成员管理、令牌管理、角色与成员关系管理。一个组至少保留一名所有者，所有权可转让。 |
| **协管员（MANAGER）** | 组的成员：只能做角色与成员关系管理，不能管理组设置、成员、令牌。 |
| **组访问令牌** | 平台唯一凭证体系（个人访问令牌）下的一种**主体变体**，绑定某一个角色组。用途：第三方消费方携带它调用开放角色供给接口。只读、可轮换、可撤销、作用域固定为该组。不引入第二套密钥体系。 |
| **全局令牌** | 平台管理员创建、作用域为**全部角色**的令牌，对应"超级管理员的密钥查所有"。 |
| **开放角色供给接口** | 平台对第三方暴露的唯一"角色+成员关系"查询通道，携带组令牌或全局令牌访问。 |
| **平台管理员** | 持有平台最高管理角色（超级管理员/管理员）的用户。 |

## 三、总体架构

系统由四个面组成，职责互不重叠：

1. **管理面**：委派者/平台管理员在"角色组管理"页面维护角色组、组角色、成员关系、令牌。
2. **供给面**：第三方消费方携带令牌，经开放角色供给接口读取成员关系（全量 + 增量）。
3. **个人中心**：所有登录用户查看自己拥有的角色与参与的角色组。
4. **平台管理员监督**：查看并处置所有角色组与令牌。

**凭证体系**：全平台只有一套访问令牌体系（既有的个人访问令牌）。组访问令牌、全局令牌都是这套体系下的"主体变体"，仅绑定主体（用户 / 角色组）与作用域不同，不新增第二种密钥。这样用户、权限、角色、密钥都统一在平台自身的 RBAC 与令牌模型内。

## 四、功能规格

### 4.1 委派权限

- 权限通过平台既有角色体系授予：用户先拥有平台的某个角色，再在该角色上配置"委派角色组管理 + 委派用户分配"。
- 两个权限必须同授同撤，系统必须拒绝任何"只给其一"的配置。
- 持有委派权限后，"角色组管理"入口出现在该用户的系统管理导航中。

### 4.2 角色组管理

- **创建**：委派者可创建角色组，创建者自动成为所有者。
- **重命名**：所有者可修改组名与备注。
- **删除**：组内仍存在角色（含已绑用户的角色）时不允许删除；组角色需先清空或转移。
- **列表**：委派者看到"我参与的角色组"；平台管理员看到全部角色组。
- **入口**：独立的"角色组管理"菜单，位于系统管理目录下，与"角色管理"并列，两者功能不混。

### 4.3 组角色

- 组管理员可在组内创建角色，字段：角色编码、角色名称、备注。
- 组角色是**成员集合**，创建与编辑时**不得配置任何平台权限**；它不改变被授予用户在本平台的功能权限，仅用于成员关系管理与对外供给。
- 组角色归创建它的组所有；该组的管理员可编辑、删除；已绑定用户的角色不可删除。
- 平台管理员不可见该组的组角色细节之外的数据（除监督需要）。

### 4.4 全局角色

- 平台管理员维护全局角色，并可把任意角色标记为"全局可见"或"系统级"。
- 全局角色对所有组可见，任意组管理员都可对其授予/移除用户，任意组令牌都能读取其成员。
- "普通用户"类基础角色默认全局可见；内置管理角色（如超级管理员、管理员）默认系统级，不向委派者暴露。
- 只有平台管理员能修改角色作用域，委派者无权修改任何角色的作用域。

### 4.5 授予/移除用户（成员关系管理）

- 组管理员可对"本组角色"或"全局角色"授予/移除用户。
- **隐私约束**：用户检索与展示只显示飞书公开姓名，不显示工号、邮箱、手机、部门等任何其他字段。
- 交互：搜索、多选、批量应用、逐个移除；移除即时生效。
- 授予/移除即时生效：被授予用户立即在个人中心看到该角色；开放供给接口的全量与增量结果同步反映。
- **权限约束**：委派者只能分配普通级别的角色，不得把管理员/超级管理员级别的角色授予任何用户（即使该角色被误标为全局可见）。

### 4.6 组协作（成员管理）

- 所有者可邀请**任何人**加入组为成员，并指定其为所有者或协管员。
- 所有权可转让；移除成员时组内至少保留一名所有者。
- **管理能力的双重门禁**：成员身份决定"属于哪个组"，委派权限决定"能否真的管理"。被邀请但未持委派权限的成员：
  - 不可见"角色组管理"入口（导航与接口双重拦截）；
  - 可在个人中心看到自己参与的角色组。
- 协管员不能管理组设置、成员、令牌。

### 4.7 组访问令牌与全局令牌

- **组访问令牌**：
  - 由组所有者创建、轮换、撤销、重看；协管员不可管理令牌。
  - 作用域固定为创建它的角色组，创建后不可变更。
  - 只读：只能用于开放角色供给接口，不能调用任何管理或写入能力。
  - 返回范围 = 本组角色 + 全局角色。
- **全局令牌**：
  - 由平台管理员创建、轮换、撤销。
  - 返回范围 = 全部角色。
- 通用规则：
  - 可设有效期；撤销立即生效；轮换使旧值立即失效。
  - 令牌完整值只在创建时一次性展示；重看需额外鉴权并留审计。
  - 令牌完整值不进入任何列表、日志、审计详情。

### 4.8 开放角色供给接口

- **全量查询**：携带令牌，返回该令牌作用域内的全部角色及其成员（成员仅公开姓名），供消费方建立初始快照。
- **增量同步**：基于变更游标返回自上次同步以来的成员变更（含新增与移除），消费方持续轮询维持快照；移除事件必须包含，以便回退。
- **作用域隔离**：一个组令牌永远看不到其他组的角色与成员；这是硬性约束。
- 只读；令牌撤销立即失效；消费方在令牌轮换后需用新值继续同步。
- 该接口是平台对外唯一供给通道；权限层的本地映射由消费方在自身平台完成。

### 4.9 个人中心「我的角色」

- 任意登录用户可在个人中心查看：
  - 我当前拥有的全部角色（含组角色与全局角色）及其归属；
  - 我作为成员参与的角色组及我在其中的身份（所有者/协管员）。
- 目的：成员被授予新角色后能立即发现自己多了角色；被邀请进组的人能看到自己的参与关系。

### 4.10 平台管理员能力

- 维护用户。
- 维护全局角色与系统角色；标记/切换角色作用域（全局/系统级）。
- 查看并管理**所有**角色组（含委派者创建的）：管理组、处置组角色、强制轮换或撤销任意令牌、删除角色组。
- 创建与管理全局令牌。
- 管理员视角的角色列表需展示每个角色的作用域，并允许切换。

## 五、可见性与授权规则

**谁能看到哪些角色：**

| 主体 | 可见角色 | 可见角色组 |
|---|---|---|
| 平台管理员 | 全部（全局 + 组 + 系统级） | 全部 |
| 委派者（组管理员） | 本组角色 + 全局角色 | 自己参与的角色组 |
| 组员但未持委派权限 | 仅个人中心可见自己的角色与角色组 | 个人中心只读 |
| 普通用户 | 仅个人中心可见自己的角色 | 不适用 |

**谁能对哪些角色授予/移除用户：**

| 主体 | 可操作角色 | 约束 |
|---|---|---|
| 平台管理员 | 任意角色 | — |
| 委派者 | 本组角色 + 全局角色 | 仅普通级别角色，不得分配管理级角色 |

**令牌可见范围：**

| 令牌 | 可见角色 |
|---|---|
| 组令牌 | 本组角色 + 全局角色 |
| 全局令牌 | 全部角色 |

## 六、安全红线（不可违反的不变式）

1. **组角色不携带本平台任何权限**，不能通过创建组角色获得或授予任何平台管理能力。
2. **组令牌只读且仅限供给接口**，不能调用任何管理/写入接口；不继承创建者个人权限。
3. **委派者不得分配管理级角色**（平台管理员、超级管理员级别），即使角色被误标为全局可见。
4. **角色作用域只能由平台管理员修改**；委派者无权修改。
5. **委派权限不可拆分**：委派角色组管理与委派用户分配必须同时存在。
6. **令牌作用域不可越界**：组令牌数据作用域固定为所属组；作用域隔离是硬约束。
7. **令牌完整值不落日志**；撤销立即生效；轮换使旧值立即失效。
8. **被邀请者未持委派权限时无管理入口**，只有个人中心可见性。
9. **作用域为系统级的角色对委派者完全不可见**。

## 七、范围边界（明确不做的事）

- 不改变既有第三方系统直连 OpenLDAP 的登录认证方式。
- 不承担第三方系统的权限层（权限映射与授权在消费方本地）。
- 不引入第二种密钥体系（组令牌是现有令牌体系的变体）。
- 不做移动端适配。

## 八、验收要点

按以下可验证行为验收：

1. 授予某用户委派权限前，其系统管理导航无"角色组管理"入口；授予后出现。
2. 委派者创建角色组后成为所有者；可在组内创建角色、对角色授予/移除用户。
3. 授予用户时只能看到并搜索公开姓名，其他用户字段不可见。
4. 被授予用户立即能在个人中心看到新角色。
5. 组令牌只能读到本组角色 + 全局角色；看不到其他组的任何角色；撤销后立即失效。
6. 全局令牌能读到全部角色。
7. 委派者尝试把管理级角色授给用户被拒绝；尝试修改角色作用域被拒绝。
8. 组角色不授予任何平台权限，被授予用户在本平台的功能权限不因该角色改变。
9. 增量同步能正确返回新增与移除的成员变更，消费方可据此维持与全量一致的快照。
10. 平台管理员能看到全部角色组，能处置任意组与令牌，能标记角色全局可见/系统级。
11. 被邀请但未持委派权限的成员看不到管理入口，仅个人中心可见参与关系。
12. 令牌完整值不出现在任何列表与日志中。
