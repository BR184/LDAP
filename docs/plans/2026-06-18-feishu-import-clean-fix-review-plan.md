# 飞书导入计划式重构问题修复审核方案

**状态：** Proposed

**日期：** 2026-06-18

**目标：** 对当前飞书计划式导入测试中暴露的问题做一次完整修复方案设计。方案只保留一套权威导入链路，不通过兼容旧逻辑、追加临时分支或前端遮掩来修补问题。

---

## 1. 当前确认的问题

### 1.1 上级权限没有随导入自动生成

当前导入可以解析并写入 `leader_ref`，但执行导入后没有根据上下级关系自动派生角色。

现状影响：

- 被导入为直属上级的人不会自动拥有直属下属密码重置权限。
- 多层管理者不会自动拥有递归下级密码重置权限。
- 权限需要人工再去角色管理或用户管理中补，导入结果不完整。

根因：

- `leader_ref` 只是作为用户字段保存。
- 导入执行链路只给新用户默认绑定 `NORMAL_USER`。
- 当前没有组织关系到角色的派生服务。

### 1.2 第二次导入无法识别离职人员

当前计划生成只遍历导入文件中的用户。文件中不存在的人不会进入 diff 计算，因此不会生成 `RESIGN` 或 `DISABLE` 变更项。

正确行为：

- 系统内存在、来源为飞书、当前在职或启用的用户，如果本次飞书文件缺失，应在计划中显示为离职/停用候选项。
- 用户在计划详情中确认后，执行时再停用账号、同步 LDAP 状态并移出 LDAP 组。

### 1.3 计划详情按字段行展示，业务用户难以理解

当前 `UPDATE` 被拆成字段级变更项后直接展示给前端，用户看到的是 `deptCode`、`leaderRef`、`jobTitle` 等字段变化，而不是“某个人发生了什么变化”。

正确行为：

- 底层仍保留字段级变更，服务于执行、撤回和审计。
- 前端审核视图必须按对象聚合，一人一行、一部门一行。
- 字段明细只放在展开行或抽屉中查看。

### 1.4 计划详情页面高度不可控

当前页面直接全量展开 `changeItems`。人员数量多时，页面会变得非常长，计划列表和计划详情的操作位置也不顺手。

正确行为：

- 上方区域：左侧生成计划，右侧计划列表。
- 下方区域：当前计划详情。
- 详情表固定高度，配合分页、筛选和搜索。

### 1.5 默认部门 `D001` 已实际落库为 `????`

已核实当前数据库：

```sql
SELECT dept_code, dept_name, HEX(dept_name)
FROM sys_department
WHERE dept_code = 'D001';
```

结果：

```text
D001 | ???? | 3F3F3F3F
```

这不是前端显示问题，而是数据库中已经存成四个问号，原始中文已经丢失。`admin` 用户姓名、`SUPER_ADMIN`、`ADMIN`、`NORMAL_USER` 角色名当前落库是正常中文，因此问题集中在默认部门初始化/迁移过程。

## 2. 目标架构

飞书导入最终只保留一条权威链路：

```text
上传/选择文件
  -> 生成导入计划
  -> 对象级预览
  -> 人工确认
  -> 执行 MySQL + LDAP
  -> 组织角色自动派生
  -> 可重试 LDAP 失败
  -> 可生成撤回计划
  -> 可执行撤回
```

禁止保留两套导入语义：

- 不再暴露 `SUPPLEMENT` / `ALIGN` 模式。
- 不再保留可被前端或接口调用的旧直接导入链路。
- 不用前端隐藏问题来替代后端一致性设计。

---

## 3. 默认角色与权限设计

### 3.1 默认内置角色清单

需要明确维护以下系统内置角色：

| 角色编码 | 角色名称 | 来源 | 说明 |
| --- | --- | --- | --- |
| `SUPER_ADMIN` | 超级管理员 | 系统内置 | 拥有全部管理权限，可重置所有人密码 |
| `ADMIN` | 管理员 | 系统内置 | 常规系统管理角色，具体权限由角色管理配置 |
| `NORMAL_USER` | 普通用户 | 系统内置 | 所有导入用户默认拥有 |
| `DIRECT_MANAGER` | 直属上级 | 系统自动派生 | 至少有一级直属下属的用户自动拥有 |
| `TREE_MANAGER` | 多级上级 | 系统自动派生 | 拥有多层下级链路的用户自动拥有 |

### 3.2 默认权限绑定

| 角色编码 | 默认权限 |
| --- | --- |
| `DIRECT_MANAGER` | `USER_PASSWORD_RESET_DIRECT` |
| `TREE_MANAGER` | `USER_PASSWORD_RESET_DIRECT` + `USER_PASSWORD_RESET_TREE` |
| `SUPER_ADMIN` | `USER_PASSWORD_RESET_ALL`、`USER_PASSWORD_RESET_DIRECT`、`USER_PASSWORD_RESET_TREE` 以及其他管理权限 |

说明：

- `DIRECT_MANAGER` 只表示可以重置直属下属密码。
- `TREE_MANAGER` 表示可以重置自己管理链路下所有层级下属密码。
- `TREE_MANAGER` 的权限能力包含 `DIRECT_MANAGER`，即递归下级密码重置权限是直属下属密码重置权限的超集。
- 如果一个用户同时符合直属上级和多级上级条件，可以同时拥有 `DIRECT_MANAGER` 和 `TREE_MANAGER` 两个派生角色，便于页面展示和审计；权限能力上 `TREE_MANAGER` 已包含直属场景。

## 4. 组织角色自动派生规则

### 4.1 派生输入

只基于平台当前有效用户关系计算：

- 用户未删除。
- 用户状态为启用或在职。
- `leader_ref` 指向另一个有效用户的 `user_id`。

无效关系不参与派生：

- `leader_ref` 为空。
- `leader_ref` 指向不存在用户。
- 上下级关系形成循环。
- 目标上级已离职或停用。

### 4.2 直属上级角色

如果用户 A 被至少一个有效用户的 `leader_ref` 直接引用，则 A 应自动拥有：

```text
DIRECT_MANAGER
```

该角色提供：

```text
USER_PASSWORD_RESET_DIRECT
```

### 4.3 多级上级角色

如果用户 A 的下级链路深度大于 1，也就是存在：

```text
A -> B -> C
```

则 A 应自动拥有：

```text
TREE_MANAGER
```

该角色提供：

```text
USER_PASSWORD_RESET_DIRECT
USER_PASSWORD_RESET_TREE
```

示例：

| 关系 | 自动角色 |
| --- | --- |
| A 是 B 的直属上级，B 没有下属 | A 获得 `DIRECT_MANAGER` |
| A 是 B 的直属上级，B 是 C 的直属上级 | A 获得 `DIRECT_MANAGER` + `TREE_MANAGER`，B 获得 `DIRECT_MANAGER` |
| A 是 B 的直属上级，B 是 C 的直属上级，C 是 D 的直属上级 | A 获得 `DIRECT_MANAGER` + `TREE_MANAGER`，B 获得 `DIRECT_MANAGER` + `TREE_MANAGER`，C 获得 `DIRECT_MANAGER` |

### 4.4 派生时机

以下动作完成后必须重新计算组织派生角色：

- 飞书导入计划执行完成。
- 飞书导入撤回完成。
- 用户手工新增、编辑、停用、删除。
- 部门或用户关系批量修复。

### 4.5 派生角色不能覆盖人工角色

当前 `assignRoles` 是覆盖式角色绑定，会先删除用户全部角色再重写。该方法不能用于组织角色派生。

需要新增正式能力：

```text
addRoleIfAbsent(userId, roleCode)
removeRoleIfPresent(userId, roleCode)
syncDerivedRoles(roleCode, expectedUserIds)
```

派生服务只管理 `DIRECT_MANAGER` 和 `TREE_MANAGER` 两个系统自动派生角色，不修改用户的其他人工角色。

## 5. 导入计划生成修复

### 5.1 用户匹配

继续坚持当前正确身份模型：

```text
飞书 user_id = sys_user.user_id = LDAP uid
```

新用户使用导入文件中的飞书 `user_id` 创建平台用户。

### 5.2 离职识别

生成计划时增加全量对比：

1. 解析本次文件中的全部 `user_id`。
2. 查询平台内来源为飞书、未删除、当前有效的用户。
3. 找出“平台存在但本次文件缺失”的用户。
4. 为这些用户生成 `RESIGN` 或 `DISABLE` 计划项。

建议统一使用 `RESIGN` 表达业务语义，执行时落地为：

- `employment_status = RESIGNED`
- `status = DISABLED`
- LDAP 用户停用
- LDAP 组成员关系移除

### 5.3 风险与确认

离职项不需要额外保守阻断，因为导入流程已经要求人工确认。但必须在计划详情中清晰展示：

```text
本次文件缺失，执行后将标记离职并停用账号。
```

## 6. 计划详情展示修复

### 6.1 后端保留字段级变更

`sys_import_change_item` 仍保存字段级变更，用于：

- 精确执行。
- 撤回恢复。
- 审计追踪。
- LDAP 失败补偿。

### 6.2 新增对象级审核视图

新增或重构详情响应，提供面向页面展示的对象级结构：

```text
ImportPlanReviewResponse
  - batch
  - summary
  - userRows
  - departmentRows
  - conflictRows
```

用户行建议字段：

| 字段 | 说明 |
| --- | --- |
| `targetKey` | user_id |
| `realName` | 姓名 |
| `employeeNo` | 工号 |
| `deptCode` | 主部门 |
| `jobTitle` | 岗位 |
| `leaderRef` | 直属上级 user_id |
| `directLeaderRaw` | 飞书原始直属上级 |
| `status` | 账号状态 |
| `employmentStatus` | 在职状态 |
| `changeType` | 新增/修改/离职/冲突 |
| `riskLevel` | 风险等级 |
| `enabled` | 是否执行 |
| `requiresConfirmation` | 是否需要确认 |
| `fieldDiffs` | 字段明细 |

前端默认展示对象行，展开后查看 `fieldDiffs`。

### 6.3 页面布局

页面布局调整为：

```text
┌──────────────────────┬──────────────────────┐
│ 生成计划              │ 计划列表              │
└──────────────────────┴──────────────────────┘
┌──────────────────────────────────────────────┐
│ 当前计划详情                                  │
│ 筛选 / 搜索 / 统计                            │
│ 固定高度表格 + 分页                           │
└──────────────────────────────────────────────┘
```

详情筛选：

- 全部
- 新增
- 修改
- 离职
- 冲突
- 失败
- LDAP 失败

## 7. 批次状态与撤回修复

### 7.1 活动批次判断

当前活动批次判断只看状态，过期草稿也可能阻止新计划生成。

修复规则：

| 状态 | 是否阻止新计划 |
| --- | --- |
| `DRAFT` 且未过期 | 是 |
| `DRAFT` 但已过期 | 否，应自动标记 `EXPIRED` 或允许取消 |
| `CONFIRMED` | 是 |
| `EXECUTING` | 是 |
| `FAILED` | 否，但页面提示存在失败批次 |
| `COMPLETED` | 否 |
| `ROLLED_BACK` | 否 |
| `EXPIRED` | 否 |
| `CANCELLED` | 否 |

建议新增状态：

```text
EXPIRED
CANCELLED
```

### 7.2 撤回计划幂等

同一个批次只能有一份有效撤回计划。

规则：

- 未执行的撤回计划重复生成时，应覆盖旧的 `PENDING` 撤回项或直接返回现有计划。
- 已撤回批次不允许再次撤回。
- 撤回执行完成后必须重新计算 `DIRECT_MANAGER` 和 `TREE_MANAGER` 派生角色。

## 8. 默认部门乱码修复方案

### 8.1 问题结论

当前 `D001` 的 `dept_name` 已实际落库为：

```text
????
```

十六进制：

```text
3F3F3F3F
```

这表示原始中文已经被替换为问号，不是前端编码显示问题。

### 8.2 正确修复

新增数据库迁移，明确修复系统默认部门。最终名称固定为 `系统后台`，不使用 `admin` 作为部门名称：

```sql
UPDATE sys_department
SET dept_name = '系统后台'
WHERE dept_code = 'D001'
  AND source_type = 'MANUAL';
```

同时检查并修复所有系统内置中文基础数据：

- `sys_department`
- `sys_role`
- `sys_permission`
- `sys_menu`

不建议只在前端做显示替换，因为数据本身已经错误。

### 8.3 编码治理

后续所有迁移文件必须统一保存为 UTF-8。数据库连接和 MySQL 已是 `utf8mb4`，当前数据库变量正常，因此重点是迁移文件和构建过程不能再污染中文。

## 9. 实施阶段建议

### Phase 1：数据与角色基础

- 新增 `DIRECT_MANAGER` 角色。
- 新增 `TREE_MANAGER` 角色。
- 绑定 `DIRECT_MANAGER -> USER_PASSWORD_RESET_DIRECT`。
- 绑定 `TREE_MANAGER -> USER_PASSWORD_RESET_DIRECT + USER_PASSWORD_RESET_TREE`。
- 修复 `D001` 默认部门名称为 `系统后台`。
- 检查并修复内置角色、权限、菜单中文基础数据。

### Phase 2：角色派生服务

- 新增 `LeaderRoleDerivationService`。
- 新增角色合并/派生同步仓储方法。
- 实现直属上级和多级上级识别。
- 防止循环上下级关系导致递归异常。
- 导入执行、撤回、用户编辑后触发派生重算。

### Phase 3：导入计划生成

- 增加本次文件用户集合与系统现有飞书用户集合的全量对比。
- 生成缺失用户的 `RESIGN` 计划项。
- 离职执行时统一停用平台账号、LDAP 账号和 LDAP 组关系。

### Phase 4：计划详情审核视图

- 新增对象级审核 DTO。
- 按用户/部门聚合字段级变更。
- 前端改为对象级表格展示。
- 支持固定高度、分页、搜索、筛选。

### Phase 5：状态机与撤回

- 新增 `EXPIRED`、`CANCELLED` 状态。
- 修正活动批次判断。
- 撤回计划生成幂等化。
- 撤回后重新计算组织派生角色。

### Phase 6：旧链路清理

- 删除或下线旧直接导入入口。
- 保留一套 `/api/v1/import/plan` 权威接口。
- 清理前端对旧接口的引用。
- 清理不再使用的旧导入模式代码。

## 10. 验收标准

- 首次导入后，所有用户正确进入用户管理。
- 被别人直接引用为上级的人自动获得 `DIRECT_MANAGER`。
- 存在多级下级链路的管理者自动获得 `TREE_MANAGER`。
- 直属上级只能重置直属下属密码。
- 多级上级可以重置完整下级链路内用户密码。
- 第二次导入缺失人员会生成离职计划项。
- 计划详情一人一行，字段变化可展开查看。
- 大量人员导入时页面不会无限拉长。
- 过期草稿不会阻塞新导入。
- 撤回计划重复生成不会产生重复撤回项。
- 撤回后组织派生角色重新计算。
- `D001` 默认部门显示为正常中文，例如 `系统后台`。
- 不存在两套可调用的飞书导入主流程。

---

## 11. 不采用的做法

- 不在前端把 `????` 硬编码显示成中文。
- 不用 `assignRoles` 覆盖用户全部角色来补上级权限。
- 不保留旧导入模式作为备用入口。
- 不把字段级 diff 直接作为主要审核界面。
- 不为了绕过活动批次问题而手动清数据库状态。
- 不新增外部身份绑定表，继续坚持 `飞书 user_id = sys_user.user_id = LDAP uid`。
