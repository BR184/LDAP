# 角色治理与角色组可用性改进设计

## 背景与目标

本次改进解决角色作用域调整、角色授权效率、委派管理首次进入报错以及角色组归属信息表达不清的问题。既有 RBAC 权限、角色和角色组模型保持权威，不引入平行授权结构，不修改已发布的角色、当前用户、LDAP 与兼职部门 API 契约。

## 一、角色作用域治理

- 平台管理员可以在 `SYSTEM`、`GLOBAL`、`GROUP` 三种作用域之间调整角色。
- 切换到 `GROUP` 时必须显式选择目标角色组，不能沿用历史角色组或隐式推断。
- 后端继续执行既有不变式：绑定平台权限的角色不能进入 `GROUP` 作用域。
- 角色列表支持多选作用域筛选，未选择时表示全部；任意组合按“或”关系过滤。

## 二、常用权限套件

- 权限套件是角色授权界面的批量选择快捷方式，不是新的权限层。
- 套件使用版本化 JSON 资源定义，包含稳定 ID、显示名称、顺序和权限编码列表。
- 系统启动时校验资源版本、套件 ID 唯一性、套件内权限编码唯一性，以及每个权限编码真实存在。
- 新增只读目录接口返回套件及其解析后的权限 ID，前端据此操作现有权限树。
- 勾选套件等价于勾选其全部细粒度权限；取消套件时保留仍被其他已选套件需要的权限。
- 用户可以继续单独增删细粒度权限，最终提交仍然只有既有权限 ID 集合。

初始套件：

1. 角色组管理完整权限。
2. 用户管理只读权限。
3. 角色管理完整权限。

## 三、委派页面查询隔离

- 角色组相关查询缓存键必须包含当前登录用户 ID，禁止跨登录用户复用列表和详情缓存。
- 登录用户变化时清空当前选中的角色组。
- 角色、协作者和令牌等从属查询只能在角色组列表成功且所选角色组属于当前列表时启动。
- 组令牌查询只对当前组所有者或平台管理员启动。
- 修复目标是消除错误请求源头，不通过吞掉错误消息或增加回退分支处理。

## 四、角色组归属与访问身份

角色组列表和详情直接展示三个互不混淆的概念：

- `创建者`：由角色组既有 `creator` 用户标识解析出的公开姓名。
- `所有者`：当前 OWNER 成员的公开姓名列表。
- `我的身份`：当前用户在组内的 OWNER 或 MANAGER 身份。
- 平台管理员不属于组成员时展示 `访问身份：平台管理员监督`，不能伪装成组所有者。

创建者不存在时接口返回 `null`，前端显示“未知用户”。所有者返回公开姓名数组。该扩展仅发生在新角色组 API，不修改已有公共 DTO。

## 五、兼容性边界

- `RoleResponse`、`CurrentUserResponse`、LDAP API 及兼职部门数组字段保持不变。
- 只新增权限套件读取接口，并扩展尚处于开发期的角色组响应。
- 不修改端口、Docker 服务名、MySQL、LDAP 配置或现有业务数据。
- 本次不做移动端适配，也不使用浏览器自动化验证。

## 六、验收标准

1. 系统级或全局角色选择角色组并确认后可变为组角色；未选择目标组不能提交。
2. 角色列表可按一种或多种作用域筛选并可重置。
3. 角色授权可一键选择常用权限套件，仍可编辑单项权限，提交结果与权限树一致。
4. 管理员退出后由委派用户首次进入角色组管理，不会请求无权访问的旧角色组，也不会连续出现多条错误。
5. 角色组列表和详情明确显示创建者、所有者以及当前用户访问身份。
6. 后端测试、前端类型检查和生产构建通过；通过非浏览器 HTTP 请求验证新增接口。
