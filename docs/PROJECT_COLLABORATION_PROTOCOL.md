# 项目协作规范

**文档版本**: 1.0  
**生效日期**: 2026-06-18  
**适用项目**: LDAP 企业统一身份管理平台 (corp-idm-platform)

---

## 1. 团队角色与职责

### 1.1 角色定义

| 角色 | 成员 | 职责 |
|------|------|------|
| **产品负责人** | 高健峰 | 需求确认、业务规则定义、最终验收 |
| **项目经理** | Claude Code | 设计方案统筹、架构设计、与产品和开发协作、文档审核 |
| **开发工程师** | CODEX | 代码实现、单元测试、技术方案细化 |

### 1.2 协作模式

- **所有成员在同一工作目录 `E:\ldap` 下协作**，文件共享
- **信息由产品负责人（高健峰）传递**
- 项目经理不直接参与代码编写，通过产品负责人向开发工程师传达任务
- 开发工程师的反馈和问题通过产品负责人回传给项目经理

## 2. 设计与开发流程

### 2.1 标准工作流

```
产品需求
    ↓
项目经理：设计方案、编写设计文档
    ↓
产品负责人：审核设计、确认业务规则
    ↓
项目经理：输出开发任务（通过产品负责人）
    ↓
开发工程师：代码实现前核实现状
    ↓
开发工程师：编码、测试、提交
    ↓
项目经理：代码审核、架构对齐检查
    ↓
产品负责人：功能验收
```

### 2.2 设计阶段

**项目经理职责**：
1. 根据需求编写设计文档（存放在 `docs/plans/` 或 `docs/Design/`）
2. 设计文档应包含：
   - 背景和目标
   - 核心概念定义
   - 业务规则
   - 数据模型
   - 接口设计
   - 实施阶段
   - 验收标准
3. 设计文档经产品负责人审核后定稿

### 2.3 开发阶段

**项目经理职责**：
- 将设计方案转化为开发任务
- 通过产品负责人向开发工程师传达任务
- 任务应包含：任务目标、关键约束、参考文档、验收标准

**开发工程师职责**：
1. **收到任务后，先快速调研核实当前代码的实际情况**
2. **以代码现状为准进行校对**
3. 如发现设计文档描述与代码实际不一致，先反馈（通过产品负责人）
4. 如果确认无误，则直接按项目规范开始编码
5. **任务目标保持不变**：即使有细微的技术实现差异，核心业务目标不变
6. 如果只有细微的不影响整体编码的区别，在完成编码任务后的报告内提及反馈

## 3. 任务传达格式

### 3.1 项目经理 → 开发工程师

当项目经理需要通过产品负责人向开发工程师传达指令时，使用以下格式：

```
=====
TO CODEX:
=====
（任务内容）
=====
```

**必须附带以下备注**：

> **重要说明**：以上内容来自项目经理（对方不直接参与代码编写），部分描述可能与实际代码有细微偏差。请在正式开始改动前，先快速调研核实当前代码的实际情况，以代码现状为准进行校对。如发现与描述不一致的地方，请先反馈；如果确认无误，则直接按项目规范开始编码。任务目标保持不变，如果只有细微的不影响整体编码的区别，你需要在完成编码任务后的报告内提及反馈。

### 3.2 开发工程师 → 项目经理

开发工程师完成任务后，应通过产品负责人提交报告，包含：

1. **任务完成情况**：已完成的功能点
2. **代码变更范围**：修改的文件列表
3. **实际实现与设计文档的差异**（如有）
4. **遗留问题**（如有）
5. **建议的后续优化**（可选）

## 4. 开发规范

### 4.1 代码架构规范

本项目采用 **DDD（领域驱动设计）分层架构**：

```
interfaces (接口层)
    ↓ 调用
application (应用服务层)
    ↓ 编排
domain (领域层)
    ↓ 依赖
infrastructure (基础设施层)
```

**禁止跨层调用**：
- ❌ interfaces 直接调用 infrastructure
- ❌ application 绕过 domain 直接操作数据库
- ✅ 严格遵守依赖方向：interfaces → application → domain ← infrastructure

### 4.2 核心身份模型规范

**铁律**：

```
飞书 user_id = 平台 sys_user.user_id = LDAP uid
```

**禁止**：
- ❌ 引入外部身份绑定表 `sys_user_external_identity`
- ❌ `sys_user.user_id` 与飞书 user_id 不一致
- ❌ LDAP uid 与 `sys_user.user_id` 不一致
- ❌ 使用 `external_id` 字段（已在 V25 迁移中删除）

**理由**：
- V24/V25 迁移已明确将 `external_id` 合并到 `user_id` 并删除独立字段
- 飞书是公司唯一人员主数据源
- 统一身份模型降低复杂度

### 4.3 命名规范

| 概念 | Java 变量名 | 数据库字段 | LDAP 属性 |
|------|------------|-----------|----------|
| 用户ID | `userId` | `user_id` | `uid` |
| 工号 | `employeeNo` | `employee_no` | `employeeNumber` |
| 显示名 | `name` | `name` | `cn` |
| 邮箱 | `email` | `email` | `mail` |
| 手机号 | `mobile` | `mobile` | `mobile` |
| 部门编码 | `deptCode` | `dept_code` | `departmentNumber` |
| 账号状态 | `status` | `status` | `employeeType` |

**特别注意**：
- LDAP 接口参数应使用 `uid` 而非 `userId`，避免混淆（LDAP 属性名是 `uid`）
- 状态字段：MySQL 使用 `ENABLED/DISABLED`，LDAP 使用 `employeeType=ENABLED/DISABLED`

### 4.4 数据库迁移规范

- 所有数据库变更必须通过 Flyway 迁移脚本
- 迁移脚本命名：`V{版本号}__{描述}.sql`（例如 `V29__feishu_import_plan.sql`）
- 禁止修改已执行的迁移脚本
- 新迁移脚本必须向前兼容

### 4.5 LDAP 同步规范

**幂等原则**：
- 所有 LDAP 操作必须幂等
- 重复执行同一操作不应产生错误
- 接口命名应体现幂等语义：`createOrUpdate` / `disableIfExists` / `enableIfExists`

**一致性原则**：
- MySQL 写入成功但 LDAP 失败 → 标记为 `LDAP_FAILED`，进入补偿队列
- LDAP 失败项最多自动重试 3 次
- 超过重试次数后进入人工处理

### 4.6 事务边界规范

- 应用服务层（`application`）是事务边界
- 一个应用服务方法应对应一个业务用例
- LDAP 操作不在 MySQL 事务内，需补偿机制

### 4.7 测试规范

- 单元测试覆盖率要求：核心业务逻辑 ≥ 80%
- 集成测试：LDAP 相关功能必须有集成测试
- 测试数据：使用 H2 内存数据库 + Stub LDAP 实现

## 5. 文档规范

### 5.1 设计文档

**存放位置**：`docs/plans/` 或 `docs/Design/`

**命名格式**：`YYYY-MM-DD-{功能简称}-{文档类型}.md`

例如：
- `2026-06-17-feishu-import-plan-and-rollback-design.md`
- `2026-06-18-ldap-consistency-compensation-design.md`

**必须包含章节**：
1. 文档概述（状态、日期、目标）
2. 核心概念定义
3. 业务规则
4. 数据模型
5. 接口设计
6. 实施阶段
7. 验收标准

### 5.2 进度记录

**存放位置**：`docs/progress/`

**命名格式**：`progress-{编号}-{简述}.md`

例如：`progress-029-feishu-import-plan-implementation.md`

### 5.3 运维手册

**存放位置**：`docs/runbooks/`

面向运维人员的操作手册，包括部署、配置、故障排查等。

## 6. Git 协作规范

### 6.1 分支策略

- `main` - 主分支，生产就绪代码
- `develop` - 开发分支（如需要）
- `feature/*` - 功能分支
- `bugfix/*` - 修复分支

### 6.2 提交信息规范

格式：`<type>(<scope>): <subject>`

类型（type）：
- `feat` - 新功能
- `fix` - 修复
- `refactor` - 重构
- `docs` - 文档
- `test` - 测试
- `chore` - 构建/工具

示例：
```
feat(sync): 实现飞书导入计划式预览
fix(ldap): 修复用户禁用后 LDAP 同步失败问题
refactor(user): 统一 user_id 命名规范
docs(design): 更新飞书导入设计方案
```

### 6.3 代码审核

- 所有代码变更必须经过项目经理审核
- 审核重点：
  - 是否符合架构设计
  - 是否遵守核心身份模型
  - 是否有单元测试
  - 是否有数据库迁移脚本

## 7. 常见问题

### Q1: 设计文档与代码实现有冲突怎么办？

**A**: 以代码现状为准。开发工程师发现冲突时应先反馈，项目经理更新设计文档。

### Q2: 是否可以引入新的依赖库？

**A**: 需要项目经理评审。引入新依赖应考虑：
- 是否必须
- 是否与现有技术栈一致
- 许可证是否兼容
- 维护状态是否良好

### Q3: 发现代码中有不符合规范的历史代码怎么办？

**A**: 
- 如果是修改涉及的代码，顺手修正
- 如果是大范围重构，先反馈，由项目经理评估是否立即修正或记录为技术债

### Q4: V24/V25 迁移的 `external_id` 字段是否还能使用？

**A**: **禁止使用**。该字段已在 V25 迁移中删除，所有代码应使用 `user_id`。

### Q5: 手工录入用户和飞书导入用户有什么区别？

**A**: **没有本质区别**。手工录入也必须使用飞书 `user_id`，只是来源渠道不同：
- 飞书导出文件导入：系统自动读取
- 手工录入：管理员手工填写飞书 `user_id`

不存在"临时账号"或"账号接管"概念。

## 8. 附录：关键设计决策记录

### ADR-001: 统一身份模型

**决策日期**: 2026-06-17  
**状态**: 已采纳  
**决策**: 飞书 user_id = 平台 sys_user.user_id = LDAP uid  
**理由**: 
- 飞书是公司唯一人员主数据源
- V24/V25 迁移已明确统一身份方向
- 降低模型复杂度
- 符合内网统一认证平台定位

### ADR-002: 不引入外部身份绑定表

**决策日期**: 2026-06-17  
**状态**: 已采纳  
**决策**: 不新增 `sys_user_external_identity` 表  
**理由**:
- 当前只有飞书一个身份源
- 与 V24/V25 迁移意图冲突
- 引入不必要的复杂度
- 如未来需要多身份源，可在新阶段重新评估

### ADR-003: 计划式导入替代模式选择

**决策日期**: 2026-06-17  
**状态**: Proposed  
**决策**: 将 SUPPLEMENT/ALIGN 模式替换为单一计划式导入  
**理由**:
- 用户难以理解模式差异
- 预览+确认机制更直观
- 支持撤回能力
- 便于审计和排查
